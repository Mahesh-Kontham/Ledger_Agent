## 1. Product in one paragraph

Users add bills from 4 sources (file upload, camera scan, email, manual entry). The system extracts the fields with an LLM, then verifies each bill: duplicate check, fraud-risk score, cross-verification against bank/card debits, and mandatory-field check. Each bill is routed to one status: VERIFIED, NEEDS_REVIEW, MISSING_DATA or DUPLICATE. Only VERIFIED bills (or bills a human approves) post to a double-entry ledger in INR. The ledger feeds merchant groups, budgets with pace alerts, and anomaly flags. Two modes: **Individual** and **Business**. The mode changes thresholds and ledger views only; the code paths are the same.

## 5. End-to-end pipeline (function contracts)

Every bill, from every source, goes through this exact function: `process_bill(input) -> Bill`.

```
ingest -> extract -> normalize -> verify -> route -> (if VERIFIED) post_to_ledger -> run_anomalies -> run_budget_checks
```

| Function | Module | Input | Output |
|---|---|---|---|
| `ingest_upload(file_bytes, filename)` | ingest | uploaded image/PDF | `RawBill(source='upload', file_path, file_hash)` |
| `ingest_scan(image_bytes)` | ingest | `st.camera_input` image | `RawBill(source='scan', ...)` |
| `ingest_email()` | ingest | IMAP inbox or `sample_data/inbox/*.eml` | `list[RawBill(source='email', ...)]`, one per attachment (PDF/JPG/PNG) |
| `ingest_manual(form: dict)` | ingest | manual form values | `RawBill(source='manual', fields=form, file_path=None)` |
| `extract_fields(raw)` | extract | RawBill with file | `ExtractedFields` (Section 6). Manual: fields copied, every confidence = 1.0 |
| `normalize_merchant(name)` | merchants | raw merchant string | `(merchant_normalized, category)` |
| `to_inr(amount, currency, date, matched_txn)` | fx | amount + currency | `(amount_inr, fx_rate, fx_rate_date, fx_source)` |
| `check_duplicate(bill)` | verify | Bill | `None` or `original_bill_id` |
| `check_fraud(bill)` | fraud | Bill | `FraudResult(score: int 0–100, signals: list[str])` |
| `cross_verify(bill)` | verify | Bill + unmatched transactions | `MatchResult` (Section 9.3) |
| `check_mandatory(bill, mode)` | verify | Bill | `list[str]` of missing field names |
| `decide_status(bill, mode)` | route | Bill with all check results | `(status, reasons: list[str])` |
| `post_to_ledger(bill)` | ledger | VERIFIED Bill | `list[JournalLine]`, which must balance |

## 6. LLM extraction contract

Call the model once per bill image (for a PDF, page 1 only). Use this system prompt **verbatim**:

```
You extract data from a single receipt or invoice image. Return ONLY a JSON object, no prose.
Rules:
- If a value is not clearly visible, return null for "value". NEVER guess, infer, calculate or default a value.
- "confidence" is your certainty from 0.0 to 1.0 that "value" is exactly what is printed.
- Dates in YYYY-MM-DD. Amounts as numbers without currency symbols or commas.
- currency as ISO 4217 code (INR, USD, EUR...). If no symbol or code is printed, value = null.
- line_items: only lines actually printed. fee_items: printed lines that are fees, tips, surcharges or convenience charges.
Schema:
{
 "merchant":       {"value": string|null, "confidence": number},
 "bill_date":      {"value": string|null, "confidence": number},
 "invoice_number": {"value": string|null, "confidence": number},
 "total_amount":   {"value": number|null, "confidence": number},
 "tax_amount":     {"value": number|null, "confidence": number},
 "currency":       {"value": string|null, "confidence": number},
 "payment_mode":   {"value": "CARD"|"UPI"|"CASH"|"NETBANKING"|"WALLET"|null, "confidence": number},
 "gstin":          {"value": string|null, "confidence": number},
 "line_items":     [{"description": string, "amount": number}],
 "fee_items":      [{"description": string, "amount": number}]
}
```

Post-processing rules (in code, not in the prompt):
- If `confidence < 0.85`, set that field's value to `null` and record it in `low_confidence_fields`.
- If the JSON fails to parse, retry once. If it fails again, set every field to `null` (the bill goes to MISSING_DATA with reason `"Extraction failed"`).
- Never compute a missing total from line items. Missing means missing.

## 9. Verification and routing rules (exact logic)

### 9.1 Duplicate check (runs first)
A bill is a duplicate of an existing non-REJECTED bill if ANY of these is true:
1. same `file_hash` (SHA-256 of file bytes), or
2. same `merchant_normalized` AND same `invoice_number` (both not null), or
3. same `merchant_normalized` AND same `total_amount` AND same `bill_date` (all not null).

Result: `status = DUPLICATE`, `duplicate_of = original id`. Duplicates are stored for audit but never posted.

### 9.2 Fraud check
Interface (`core/fraud.py`):
```python
class FraudChecker(Protocol):
    def score(self, file_path: str) -> FraudResult: ...   # FraudResult(score:int, signals:list[str])
```
- `MCPFraudChecker`: used when `FRAUD_MCP_URL` is set. It sends the file to the MCP server and maps the response to `FraudResult`. If the call fails, fall back to the mock and add the signal `"MCP unavailable - mock used"`.
- `MockFraudChecker` (default; deterministic):
  - EXIF `Software` tag or PDF `Producer`/`Creator` contains any of `photoshop, gimp, canva, midjourney, dall-e, stable diffusion, firefly` → score 85, signal `"Edited/generated by <tool>"`.
  - Image has no EXIF at all AND source is `scan` → score 20, signal `"No camera metadata"`.
  - Otherwise → score 10.
- Manual entries: score 0, signal `"Manual entry - no document"`.
- The UI MUST label mock scores as "Demo fraud check (mock)".

### 9.3 Cross-verification
1. Candidates = transactions with `type='DEBIT'`, `matched_bill_id IS NULL`, and `|txn_date - bill_date| <= 2 days`.
2. Prefer candidates whose lowercased description contains the bill's merchant alias. If none do, use all candidates.
3. Pick the candidate with the smallest `|variance|`.
4. If there is no candidate: `match_status = NO_MATCH`.
5. Else compute `variance = txn.amount_inr - bill.total_amount_inr` and classify in this order:
   - `|variance| <= tolerance` → `MATCHED`
   - `sum(fee_items) == variance` (±0.01) → `VARIANCE_EXPLAINED`, reason `"Fee on bill: <descriptions>"`
   - bill currency ≠ INR AND `0 < variance <= 4%` → `VARIANCE_EXPLAINED`, reason `"Forex markup"`
   - payment_mode = CARD AND `0 < variance <= max(10, 2%)` → `VARIANCE_EXPLAINED`, reason `"Probable card fee - confirm"`
   - otherwise → `VARIANCE_UNEXPLAINED`, reason `"Unexplained gap of ₹X"`
6. User-recalled amount: if `user_entered_amount` is set and differs from `total_amount` by more than the tolerance, add the info note `"You entered ₹A; invoice shows ₹B; bank debited ₹C"`. This is informational and never changes the status.
7. When a bill ends up VERIFIED, set `transactions.matched_bill_id` so the transaction cannot be matched again.

### 9.4 Mandatory fields
Missing = value is null (including fields nulled for low confidence). Use `MANDATORY_FIELDS[mode]` plus the BUSINESS GSTIN rule.

### 9.5 Status decision (`decide_status`) — first rule that applies wins

| Order | Condition | Status | Priority | Reason text example |
|---|---|---|---|---|
| 1 | duplicate found | DUPLICATE | – | "Duplicate of bill #12" |
| 2 | any mandatory field missing | MISSING_DATA | NORMAL | "Missing: bill_date, total_amount" |
| 3 | INDIVIDUAL and fraud ≥ 70 | NEEDS_REVIEW | HIGH | "Fraud risk 85%: Edited by photoshop" |
| 4 | BUSINESS and fraud ≥ 70 | NEEDS_REVIEW | HIGH | same |
| 5 | BUSINESS and fraud ≥ 40 | NEEDS_REVIEW | NORMAL | "Fraud risk 45%" |
| 6 | match_status = VARIANCE_UNEXPLAINED | NEEDS_REVIEW | NORMAL | "Unexplained gap of ₹18" |
| 7 | BUSINESS and match_status = NO_MATCH | NEEDS_REVIEW | NORMAL | "No bank/card debit found" |
| 8 | otherwise | VERIFIED | – | add warnings: fraud 40–69 (INDIVIDUAL) → "Fraud risk warning"; NO_MATCH (INDIVIDUAL) → "Single source - not bank-verified" |

### 9.6 Human review actions (Review Queue page)
- MISSING_DATA: show the bill image and a form with only the missing fields. On submit, those fields get confidence 1.0, and the bill re-runs `verify` + `route` (it is NOT auto-verified).
- NEEDS_REVIEW: buttons **Approve** (status → VERIFIED, post to the ledger, record `reviewed_at`) and **Reject** (status → REJECTED, never posted).
- Sort the queue by `review_priority` (HIGH first), then by `created_at`.

## 10. Ledger (double-entry, CA-style)

### 10.1 Chart of accounts
- Expenses: `Expense:<Category>`, `Expense:Bank Charges`, `Expense:Forex Charges`
- Assets: `Asset:Bank - <account_name>`, `Asset:Cash`, `Asset:Input GST` (BUSINESS only)
- Liabilities: `Liability:Credit Card - <account_name>`

Credit-side account:
- Matched transaction whose `account_name` contains "Card" → `Liability:Credit Card - <account_name>`
- Matched transaction otherwise → `Asset:Bank - <account_name>`
- No match → by payment_mode: CASH → `Asset:Cash`; CARD → `Liability:Credit Card - Unspecified`; all others → `Asset:Bank - Unspecified`

### 10.2 Posting rule for one VERIFIED bill
- `base = total_amount_inr`
- If BUSINESS AND `gstin` present AND `tax_amount_inr > 0`:
  - Debit `Expense:<Category>` = base − tax_amount_inr
  - Debit `Asset:Input GST` = tax_amount_inr
- Else: Debit `Expense:<Category>` = base
- If match_status = VARIANCE_EXPLAINED: Debit `Expense:Forex Charges` (forex reason) or `Expense:Bank Charges` (any other reason) = variance
- Credit the credit-side account = `txn.amount_inr` if matched, else base
- Round every line to 2 decimals. **Assert total debits == total credits.** If they are not equal, raise an error; never post an unbalanced entry.

Example (Rapido ₹125 invoice, card debited ₹130):

| entry_id | account | debit | credit | note |
|---|---|---|---|---|
| JE-000002 | Expense:Transport | 125.00 | | Rapido invoice |
| JE-000002 | Expense:Bank Charges | 5.00 | | Probable card fee - confirm |
| JE-000002 | Liability:Credit Card - HDFC Credit Card | | 130.00 | Matched txn #2 |

### 10.3 Ledger page views (MUST)
1. **Journal**: all lines grouped by entry_id, newest first.
2. **Category ledger**: total per category for the selected month.
3. **Merchant groups**: one row per merchant: count of bills, total INR, first and last date. Expand to see the bills.
4. **Trial balance**: total per account, then grand total debits = grand total credits, with a green tick if equal.
5. **GST input summary** (BUSINESS only): total `Asset:Input GST` per month.
6. **CSV export** button for the journal.

## 11. Budgets and anomalies

### 11.1 Budgets
- The Settings page sets `monthly_limit_inr` per category, per mode. Seed nothing; the user enters limits (the demo script enters Transport ₹5,000 and Advertising ₹50,000).
- `spent` = sum of the category's debit lines in the current month. `elapsed_pct = today.day / days_in_month`. `spent_pct = spent / limit`. `projected = spent / today.day * days_in_month`.
- Alerts are checked after every posting:
  - `spent_pct >= 1.00` → BUDGET_BREACH (at most once per category per month)
  - else `spent_pct >= 0.80` → BUDGET_WARNING (at most once per category per ISO week)
  - else `today.day >= 5` AND `spent_pct > 1.3 * elapsed_pct` → BUDGET_PACE (at most once per category per ISO week). Message: `"Transport: 52% of budget used by day 10 (33% of month). Projected ₹7,800 vs ₹5,000 limit."`
- Chart (MUST): plotly grouped bar per category with Spent, Projected month-end and Limit (a line marker), plus a list of alerts.
- In-app notifications only (`st.toast` on new alerts + an alerts list). Email/WhatsApp notifications: WON'T for the MVP.

### 11.2 Anomalies (rule-based; run after each posting; each creates an ANOMALY alert)
1. Amount > 3.0 × the category's 30-day average (only when ≥ 3 prior verified bills exist in that category).
2. First bill ever from this merchant AND amount ≥ ₹5,000.
3. Same merchant, same day, two or more verified bills.
4. Subscriptions category: amount > 110% of the previous bill from the same merchant ("Price increase").

## 18. Amendment: Roles & UI redesign (2026-11-14)

This section overrides Section 16's "user login and roles = WON'T". The core pipeline, the thresholds in `config.py`, the status rules and ledger posting are **unchanged**.

### 18.1 Auth & data scoping
- New table `users(id, name, email UNIQUE, password_hash, role CHECK IN ('ADMIN','BUSINESS','INDIVIDUAL'), org_name, is_active, created_at)`. Passwords are hashed with bcrypt.
- New table `audit_log(id, user_id, action, target, created_at)`. Actions logged: login, logout, upload, approve, reject, complete_fields, budget_change, csv_import, clear_data, user_create, user_deactivate, user_reactivate.
- `user_id` is added to `bills`, `transactions`, `journal_lines`, `budgets` and `alerts`. Budgets become `UNIQUE(user_id, category, mode)`. A migration on startup adds the columns and assigns pre-existing rows to `business@demo`.
- Every query in `core/db.py` filters by the logged-in user, held in a per-run ContextVar. With no user set, queries raise `PermissionError` (fail closed). Duplicate detection, bank matching, budgets and alerts are all per user.
- ADMIN gets aggregate-only functions (`admin_*`). They never return file paths, merchants, amounts or images.
- Mode is derived from role: BUSINESS → BUSINESS, INDIVIDUAL → INDIVIDUAL. The mode toggle is removed.
- `scripts/seed_users.py` creates admin@demo, business@demo and user@demo. Their passwords come from `DEMO_ADMIN_PW`, `DEMO_BUSINESS_PW` and `DEMO_USER_PW` in `.env`. The app also seeds automatically on first run if the users table is empty.
- `app.py` is a router. Unauthenticated users see only the login page. `st.navigation` shows only the logged-in role's pages, which live in `app_pages/`.

### 18.2 Three experiences
| Role | Pages | Job |
|---|---|---|
| INDIVIDUAL | Home, Add bill, Needs you, Spending, Budgets, Settings | "Am I okay?" Plain language; the journal and trial balance sit behind an "Accountant view" toggle |
| BUSINESS | Dashboard, Add bills, Review queue, Ledger, Budgets, Reports & export, Settings | "Are our books correct and is anyone cheating?" |

### 18.3 Design system
- `.streamlit/config.toml` has light and dark themes on a deep navy base, one blue accent and the Inter font.
- `assets/styles.css` is the only CSS, and it targets only `.st-key-*` hooks.
- `ui/components.py` holds the shared pieces: `money()` (₹ with Indian grouping, e.g. 1,23,456.00), `fmt_date()` ("14 Nov 2026"), `kpi_card`, `status_badge` (always shown with its reason), `bill_card`, `reason_list`, `three_way_compare`, `empty_state`, `section_header` and `process_with_progress` (pipeline steps shown live in `st.status`).
